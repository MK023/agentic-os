# Loki Fase 1.5 — piano di implementazione

> **Per chi esegue con agenti:** SUB-SKILL RICHIESTA: usare `superpowers:subagent-driven-development`
> (consigliata) oppure `superpowers:executing-plans` per eseguire questo piano task per task.
> Gli step usano checkbox (`- [ ]`) per il tracciamento.

**Goal:** dare all'hub un log store privato, interrogabile da Grafana, che risponda a
*"quale tool call è fallita in quella sessione"* — senza toccare i tre numeri pubblici.

**Architettura:** Claude Code → ingest OTLP esistente → una pipeline `logs` **nuova e
separata** nel Collector → Loki (single binary su Railway) → chunk e index su **R2**.
Grafana lo interroga sulla rete privata. Loki non riceve nessun hostname del Tunnel.

**Stack:** OpenTelemetry Collector contrib 0.158.0 · Grafana Loki 3.7.6 (single binary) ·
Cloudflare R2 (S3-compatible) · Railway · Grafana.

**Spec:** `docs/superpowers/specs/2026-08-20-loki-fase-1.5-design.md` — leggerla prima,
in particolare §4 (l'ordine dei lavori) e §5 (le due allow-list).

## Task 0: la regola WAF — MARCO, non delegabile

**Non è un task da agente.** La regola vive nella dashboard Cloudflare, fuori da git.

- [ ] **Step 1: estendere la regola su `otel.marcobellingeri.dev`**

Oggi lascia passare solo `POST /v1/metrics` con header `Authorization` presente.
Va estesa a `POST /v1/logs` con la stessa condizione sull'header.
**Il valore dell'header non si guarda, mai** — una regola WAF si legge da dashboard e
da API, quindi un token lì dentro è un segreto fuori dal secret store.

- [ ] **Step 2: misurare subito, contro produzione**

```bash
HOST=https://otel.marcobellingeri.dev
# Un token DELIBERATAMENTE invalido, in una variabile: e' la stessa forma che usa
# smoke.yml, e serve a distinguere chi risponde. 401 lo dice solo il Collector,
# 403 solo il bordo — instradare sul percorso invece che sul codice era sbagliato
# gia' una volta, il 20/08 sera.
TOKEN_INVALIDO="questo-token-non-esiste"
POST=(-X POST -H 'Content-Type: application/json' -d '{}')

for p in /v1/metrics /v1/logs; do
  echo -n "$p senza header: "
  curl -sS -o /dev/null -w '%{http_code}\n' "${POST[@]}" "${HOST}${p}"
  echo -n "$p bearer sbagliato: "
  curl -sS -o /dev/null -w '%{http_code}\n' "${POST[@]}" -H "Authorization: Bearer ${TOKEN_INVALIDO}" "${HOST}${p}"
done
echo -n "/v1/traces (deve restare chiuso): "
curl -sS -o /dev/null -w '%{http_code}\n' "${POST[@]}" "${HOST}/v1/traces"
```

Atteso **dopo** la modifica:

```
/v1/metrics senza header: 403      (bordo)
/v1/metrics bearer sbagliato: 401  (Collector)
/v1/logs senza header: 403         (bordo)
/v1/logs bearer sbagliato: 401     (Collector)
/v1/traces: 403                    (bordo, invariato)
```

Se `/v1/logs bearer sbagliato` risponde `403`, la regola non è stata estesa e **il
Task 1 non va fatto**: si fermerebbe un'asserzione vera su un comportamento assente.

## Task 3: `docker/loki.yaml`

**Dipende dal Task 2** (l'allow-list si scrive dalla misura).

**Files:**
- Create: `docker/loki.yaml`

- [ ] **Step 1: leggere la doc del fornitore PRIMA di scrivere**

```bash
# La forma esatta di object_store per un endpoint S3 NON-AWS, e il nome del flag
# di verifica della config. Non andare a memoria: qui un errore nasce silenzioso.
```
Consultare la doc Loki su *"storage configuration examples"* e *"validating
configuration"*. Serve confermare tre cose: (a) `use_thanos_objstore: true` con
`object_store.s3` è la forma corrente per un endpoint custom; (b) `bucket_lookup_type:
path` è ciò che serve a R2; (c) il flag di verifica (`-verify-config` o equivalente).
**Scrivere nel commit quale doc dice cosa.**

- [ ] **Step 2: scrivere il file**

```yaml
# Loki — Fase 1.5. Una sola copia di questa configurazione, come ogni altra in
# docker/: l'immagine Railway la copia a build time, il compose la monta.
#
# `auth_enabled: false` NON significa "senza autenticazione": in Loki riguarda il
# multi-tenancy (l'header X-Scope-OrgID), non l'accesso. Cio' che tiene chiuso
# questo servizio e' che non ha nessun hostname del Tunnel, esattamente come
# Prometheus. Non si riscriva la ragione falsa: e' gia' stata corretta una volta
# in SECURITY.md.
auth_enabled: false

server:
  http_listen_port: 3100
  # Esplicito, NON perche' il default sia diverso: il default e' "" e ascolta
  # gia' ovunque. Scritto per rendere leggibile che Grafana e il Collector sono
  # altri container. Resta sulla rete privata Railway.
  http_listen_address: 0.0.0.0

common:
  ring:
    instance_addr: 127.0.0.1
    kvstore:
      store: inmemory
  # Single binary: una sola istanza, nessuna replica. La doc lo richiede
  # esplicitamente per deploymentMode SingleBinary.
  replication_factor: 1
  path_prefix: /loki

schema_config:
  configs:
    - from: 2026-08-20
      store: tsdb
      object_store: s3
      schema: v13
      index:
        prefix: index_
        period: 24h

storage_config:
  use_thanos_objstore: true
  tsdb_shipper:
    active_index_directory: /loki/index
    cache_location: /loki/index_cache
    cache_ttl: 24h
  object_store:
    s3:
      bucket_name: ${LOKI_R2_BUCKET}
      # Endpoint R2: <ACCOUNT_ID>.r2.cloudflarestorage.com, SENZA schema.
      # ATTENZIONE, misurato: la doc Cloudflare pubblica l'endpoint CON `https://`
      # e `-verify-config` LO ACCETTA senza lamentarsi. Loki muore solo all'avvio
      # ("Endpoint url cannot have fully qualified paths"). E' l'unico errore di
      # questo file che il gate NON vede: chi incolla dal dashboard passa verde e
      # la produzione non parte.
      endpoint: ${LOKI_R2_ENDPOINT}
      access_key_id: ${LOKI_R2_ACCESS_KEY_ID}
      secret_access_key: ${LOKI_R2_SECRET_ACCESS_KEY}
      # R2 vuole region `auto`. Dichiararla evita anche la GetBucketLocation che
      # il client farebbe da solo con region vuota.
      region: auto
      # Il DEFAULT e' `auto`, NON `path`: questa riga e' una scelta, non una
      # ripetizione del default. Ammessi: auto | path | virtual-hosted.
      bucket_lookup_type: path
      # insecure resta FALSE: l'endpoint R2 e' HTTPS. Metterlo a true qui
      # significherebbe spedire le credenziali in chiaro verso internet.
      insecure: false

limits_config:
  # Senza questa riga Loki RIFIUTA il payload: la structured metadata e' il
  # meccanismo su cui poggia tutto il blocco qui sotto.
  allow_structured_metadata: true

  # ALLOW-LIST #2.
  #
  # MISURATO IL 20/08, e la prima versione di questo blocco era SBAGLIATA in modo
  # pericoloso. `ignore_defaults: true` toglie le resource attribute dall'INDICE,
  # NON le scarta: il fallback di Loki per un attributo che nessuna regola nomina
  # e' `structured_metadata`, non `drop`. Con il solo `index_label` qui sotto, un
  # payload con `user.email` fra le resource attribute produceva:
  #
  #   indice:  ["service_name"]                        <- sembrava a posto
  #   query:   {service_name="claude-code"} | user_email="victim@example.com"
  #            -> 1 risultato, con organization_id accanto
  #
  # L'indirizzo NON era una label, ma era memorizzato, indicizzato a parte e
  # interrogabile. Serve il catch-all `drop` ANCHE su resource e scope.
  #
  # `attributes:` e non `regex:`, ed e' la scelta piu' sicura: `regex` e' un regex
  # Prometheus ancorato dove il punto e' un metacarattere — misurato, con
  # `regex: service.name` un attributo chiamato `serviceXname` diventa una label.
  #
  # L'ORDINE E' LETALE: first-match-wins, quindi il catch-all va SEMPRE IN FONDO.
  # Messo prima, lo stream resta senza label e Loki risponde 400.
  otlp_config:
    resource_attributes:
      ignore_defaults: true
      attributes_config:
        - action: index_label
          attributes: [service.name]
        - action: drop
          regex: .*
    # Anche questi cadono in structured metadata per default.
    scope_attributes:
      - action: drop
        regex: .*
    log_attributes:
      # <ESITO DEL TASK 2>: qui vanno le chiavi misurate che vogliamo poter
      # filtrare — session.id e model sono le due attese. Structured metadata e
      # NON label: in Prometheus session.id e' obbligatoria, qui creerebbe uno
      # stream per sessione, che e' il primo anti-pattern di cardinalita' che la
      # doc nomina.
      - action: structured_metadata
        attributes: [session.id, model]
      # Tutto il resto cade. Non e' una delete-list: e' l'ultima riga di un
      # allow-list, e vale su ogni attributo che una versione futura inventa.
      # Ammesse: drop | index_label | structured_metadata. Per ogni voce va
      # indicato ESATTAMENTE uno fra `attributes` e `regex` — entrambi o nessuno
      # dei due fanno rifiutare la config.
      - action: drop
        regex: .*
  retention_period: 720h

compactor:
  working_directory: /loki/compactor
  # Senza questa chiave Loki RIFIUTA di partire quando retention_enabled e' true.
  # Ma il VALORE non e' validato: `delete_request_store: bananas` passa
  # -verify-config. Che `s3` sia giusto e' verificato a runtime, guardando l'URL
  # che il compactor costruisce davvero sul blocco object_store.s3.
  delete_request_store: s3
  retention_enabled: true
```

- [ ] **Step 3: verificare la config con il binario vero, non a occhio**

```bash
docker run --rm -v "$PWD/docker/loki.yaml:/etc/loki/loki.yaml:ro" \
  -e LOKI_R2_BUCKET=bucket-finto \
  -e LOKI_R2_ENDPOINT=0123456789abcdef0123456789abcdef.r2.cloudflarestorage.com \
  -e LOKI_R2_ACCESS_KEY_ID=finto -e LOKI_R2_SECRET_ACCESS_KEY=finto \
  grafana/loki:3.7.6 -config.file=/etc/loki/loki.yaml -config.expand-env=true -verify-config
```

Atteso: `config is valid`, exit 0.

**Bucket ed endpoint devono essere DIVERSI.** La prima versione di questo comando
usava `finto` e `finto.r2.cloudflarestorage.com`, e Loki rifiutava con *"the endpoint
must not prefixed with the bucket name"*: un rosso che non c'entrava nulla con la
config, su un passo che diceva "se fallisce torna alla doc".

**E questo comando NON è un oracolo.** Misurato: prende ogni nome di chiave sbagliato,
a qualsiasi profondità — quindi `config is valid` **prova** che ogni chiave esiste — ma
esce 0 anche con l'endpoint scritto `https://...`, che a runtime uccide Loki, e anche
con `delete_request_store: bananas`. I valori non li guarda.

```yaml
      # Stessa famiglia del gate sulle label delle metriche. La forma da
      # sorvegliare non e' l'elenco delle chiavi — quello cambia con il client — ma
      # che sia un ALLOW-LIST: `keep_keys` nel Collector e `ignore_defaults: true`
      # piu' un `drop` finale in Loki. Un delete-list fallisce aperto su ogni
      # attributo che una versione futura inventa, ed e' esattamente la forma che
      # questo progetto ha gia' rifiutato una volta sulle metriche.
      - name: i log passano da due allow-list, non da una delete-list

          set -euo pipefail
          python3 - <<'PY'
          import sys, yaml
          fallimenti = []

          cfg = yaml.safe_load(open("docker/otel-collector-config.yaml"))
          proc = cfg.get("processors", {})
          allow = [n for n in proc if n.startswith("transform/log-allowlist")]
          if not allow:
              fallimenti.append("il Collector non ha piu' un processor transform/log-allowlist")
          else:
              testo = yaml.safe_dump(proc[allow[0]])
              if "keep_keys" not in testo:
                  fallimenti.append("transform/log-allowlist non usa keep_keys: e' diventata una delete-list")
              pipeline = cfg["service"]["pipelines"].get("logs", {})
              if allow[0] not in pipeline.get("processors", []):
                  fallimenti.append(f"{allow[0]} esiste ma NON e' nella pipeline logs: e' come non averlo")

          # Il Collector deve avere DUE statement, non uno: keep_keys sul solo
          # contesto `log` lascia passare le resource attribute, e il 20/08 e' stato
          # misurato che `user.email` sopravvive.
          if allow:
              contesti = {st.get("context") for st in (proc[allow[0]].get("log_statements") or [])}
              if contesti != {"resource", "log"}:
                  fallimenti.append(f"transform/log-allowlist copre {sorted(contesti)}: servono resource E log, altrimenti l'identita' passa dalla resource")

          loki = yaml.safe_load(open("docker/loki.yaml"))
          limits = loki.get("limits_config", {}) or {}
          otlp = limits.get("otlp_config", {}) or {}
          if limits.get("allow_structured_metadata") is not True:
              fallimenti.append("loki.yaml non ha allow_structured_metadata: true: Loki rifiuta il payload")
          res = otlp.get("resource_attributes", {}) or {}
          if res.get("ignore_defaults") is not True:
              fallimenti.append("loki.yaml non ha ignore_defaults: true: le resource attribute finiscono nell'INDICE")

          # IL CONTROLLO CHE MANCAVA, e che -verify-config NON fa. `ignore_defaults`
          # toglie le resource attribute dall'indice ma NON le scarta: il fallback di
          # Loki e' `structured_metadata`. Senza un `drop` catch-all in FONDO a ogni
          # sezione, `user.email` resta memorizzato e interrogabile. Misurato 20/08.
          def chiude(voci, dove):
              voci = voci or []
              if not voci or voci[-1].get("action") != "drop" or voci[-1].get("regex") != ".*":
                  fallimenti.append(f"{dove} non finisce con un drop catch-all: cio' che nessuna regola nomina resta come structured metadata, interrogabile")
          chiude(res.get("attributes_config"), "resource_attributes.attributes_config")
          chiude(otlp.get("scope_attributes"), "scope_attributes")
          chiude(otlp.get("log_attributes"), "log_attributes")

          if fallimenti:
              for f in fallimenti:
                  print(f"::error::{f}")
              sys.exit(1)
          print("ok: due allow-list, entrambe chiuse")
          PY
```
